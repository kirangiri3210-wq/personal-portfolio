    Case study 01

    Campus Lost & Found

    Computer science capstone · Expo Go prototype · not a live campus service

    01The problemRead

    Campus lost-and-found usually lives on a bulletin board, in an email thread, or at a front desk. Students do not have one place to report an item, search what others posted, and message the person who lost or found it.

    02The ideaRead

    A mobile app where students can report lost and found items with optional photos, search and filter listings, see possible matches, message privately about a specific item, and mark an item recovered. It is a student project, not an official SMSU product.

    03The buildRead

    The Expo client talks directly to Firebase rather than a custom server: Authentication for email/password accounts and password reset, Cloud Firestore for items, conversations, messages, and in-app notifications, and Storage for photos. Chat uses Firestore listeners. Photos can be taken with the camera or chosen from the gallery. Listings can be moderated.

    04ArchitectureExplore

    Select a layer to see what it does. This is the verified stack — there is no custom API server.

    1. The mobile client students run in Expo Go. TypeScript throughout.

      ↓

    2. Email/password accounts and password reset. No custom auth server.

      ↓

    3. Items, conversations, messages, and in-app notifications, including live chat listeners.

      ↓

    4. Optional photos from the camera or gallery, attached to a listing.

    05TechnologyRead

    React Native, Expo, and TypeScript on the client. Firebase Authentication, Cloud Firestore, and Firebase Storage on the backend services. Matching runs on the device as a weighted comparison of report fields, not machine learning or image recognition. Pairs that reach a threshold of 40 are listed.

    06My roleRead

    This is my capstone/coursework application. I designed and built the client flows: authentication, reports, image uploads, search, matching, messaging, notifications, and moderation.

    07What I learnedRead

    I learned how to wire a mobile client to Firebase Authentication, Firestore, and Storage, including live chat with listeners. I also learned when a simple client-side score is the honest approach: it is transparent, but it is not computer vision and it is not a production campus service. Core flows are implemented. It is not on the App Store or Google Play, and there is no hosted live demo.

    Case study 02

    Talent Radar

    Southwest MN Hacks at SMSU · September 12–13, 2026 · 24 hours · 4-person team

    01The problemRead

    Skills, tickets, and succession risk usually live in separate documents. During the hackathon we wanted a single place where a manager could see who knows what, what happens if someone leaves, and how to close skill gaps.

    02The ideaRead

    Talent Radar is a workforce and skills intelligence dashboard. It maps people, skills, ticket history, and risk, then uses that data for mentorship pairing, a departure simulator, and an AI copilot over the records on file.

    03The buildRead

    In 24 hours the team shipped login, employee profiles, charts, document extraction, and chat against workforce data. I focused on the interface and on shaping the product so those pieces fit together.

    04ArchitectureExplore

    The team stack, as built for the event. Hover or click a layer. I worked on the frontend connection to this stack; I did not design the backend architecture.

    1. The dashboard UI I spent most of the weekend on: screens, charts, and product flow.

      ↓

    2. The API the frontend talked to. I collaborated on the connection; I did not own this layer.

      ↓

    3. Employee, skill, and ticket records used by the dashboard.

      ↓

    4. Copilot answers over the workforce records on file — not a general internet assistant.

    05TechnologyRead

    React and Vite on the frontend. Express and Node.js for the API, MongoDB for data, Recharts for charts, and the Google Gemini API for the copilot. I worked with the team on how the frontend connected to that stack; I did not personally design the backend architecture.

    06My roleRead

    Worked on the frontend and product idea as part of a 4-person team, while gaining exposure to backend integration and deployment. The backend was hosted in a teammate's personal hosting environment for the event. I did not own the backend architecture.

    07What I learnedRead

    A 24-hour clock forces clear product choices. I learned how a React frontend actually talks to an Express API, and I watched deployment happen in someone else's environment instead of pretending I ran it. There is a GitHub repo; there is no public live demo URL.

    Personal Portfolio Website

    Hand-built HTML, CSS, and JavaScript · this page

    01The problemRead

    I needed a public place for a resume, projects, and contact details that I could maintain myself — without a framework I do not need.

    02The ideaRead

    A single-page site that reads like an editorial document: education, three real projects, and a way to reach me. Custom domain: kirangiri.dev.

    Vanilla HTML, CSS, and JavaScript. Theme preference is stored locally. The resume opens in a dialog. Contact uses a mailto form.
